# 实机回归归档制度

> 生效：2026-08-19（A 立项「实机监测机制」步骤2 交付，门二已拍板：证据强度收紧为「仓库内可独立复核」）。
> 定位：每轮进游戏实测的证据必须按本制度归档入库；缺证据的轮次判 `FAIL_NOT_EVIDENCED`，不得只记「维护者结论」。
> 工具：判读统一走 `tools/check_logs.py`（白名单与判定铁律见其头注释与 `tools/log_noise_whitelist.json`）。

## 一、归档目录约定

每轮实机回归在 `docs/testing/<版本-轮次>/` 下归档（如 `docs/testing/v2.8-test5/`），必含：

| 文件 | 内容 | 必需 |
|---|---|---|
| `README.md` | 轮次摘要：版本线、测试包 SHA-256、结论（通过/未通过）、问题清单、例外说明 | 是 |
| `result.json` | `tools/check_logs.py` 输出（机器可读判定） | 是 |
| `清单.md` | 逐项点验清单：每项「通过/未通过/未测」＋现象＋证据位置，逐项必填 | 是 |
| `logs/` | 四份日志（error.log/game.log/setup.log/text.log）脱敏副本；`code_revisions.log` 副本 | 是 |
| `screenshots/` | 截图，命名 `NN_<检查项简称>.png`（NN＝清单序号） | 涉及界面/视觉项时必填 |
| `SHA256SUMS.txt` | 归档内所有文件的 SHA-256 清单 | 是 |

## 二、逐项必填与 FAIL_NOT_EVIDENCED

1. `清单.md` 每一项必须有结论与证据位置；空栏＝该项未测。
2. 判定规则：
   - 项结论「通过」但无证据位置（日志行/截图/自检标记）→ 该项记 `FAIL_NOT_EVIDENCED`。
   - 任何一项 `FAIL_NOT_EVIDENCED` 或「未通过」→ 本轮不得判「实机通过」，除非机主另行拍板豁免并留痕。
3. 历史轮次（v2.6-test2/v2.7-test1/v2.8-test1 等）的空白清单**不追填**（治理约定不变），只从本制度生效后的轮次起执行。

## 三、日志判读口径（与 check_logs 一致）

- `error.log`/`text.log` 全行白名单过滤：白名单外的新签名＝新错误告警；`text.log` 非 0 字节＝本地化错误签名。
- `game.log` 仅对「错误样」行（error/invalid/unknown/exception/failed/warning）告警；正常运行行忽略。
- `setup.log` 做加载摘要检查（存在性＋PRC_OCS 行数），不过滤。
- 判定铁律：`[OCS_TEST]` 标记数为 0＝本轮无效（防忘开 `-debug_mode`/未触发自检）；提供用例清单时标记数须等于清单数且全 PASS。仅「标记判读豁免」轮次例外（`--exempt-markers`，豁免事实入 result.json）。
- 游戏版本绑定：读 `code_revisions.log`；绑定失败降级人工登记版本号并记入 result.json。

## 四、脱敏

日志与截图入库前脱敏：本机用户名、绝对路径（`C:\Users\...` 等）替换为 `<REDACTED>`；`D:\SteamLibrary\...` 游戏路径保留（跨机核对清单已公开该路径口径）。脱敏后的日志副本存入 `logs/`，原始文件不入库。

## 五、与既有流程的衔接

- 本制度接入 `docs/maintenance/维护与重构标准流程.md` A/C 流程的「实机回归」环节与 `AGENTS.md` 验证门禁：实测完成后先跑 `tools/check_logs.py` 出 `result.json`，再按本制度归档；归档完成才算该轮实测闭环。
- 实机点验本身仍由维护者执行（半自动分工，门一结论 3）；AI 负责判读、脱敏、归档与报告。

## 六、黄金存档与固定实测路径

- 见 `docs/testing/黄金存档制度.md`。黄金存档是本制度中「固定复现路径」的组成部分，其哈希登记于本仓，二进制留本机归档。
