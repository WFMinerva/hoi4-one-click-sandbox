# 开工操作手册（机主版）

> 定位：给机主本人用的操作指引——新串开工、接到活时「我该说什么、做什么、在哪拍板」。
> 不懂技术也能照做。权威流程在 `docs/maintenance/维护与重构标准流程.md`（中度简化 + A/B/C 三级流程 + 三扇门），
> 当前状态看 `docs/maintenance/README_FIRST.md`，红线在 `AGENTS.md`；本手册只把「你负责的部分」挑出来，其余都是 AI 的活。

## 0. 新串开工三步（任何电脑）

1. **拉最新代码**：`git pull`（开发分支 `agent/cross-machine-governance`）。
2. **看两处状态**：
   - `docs/maintenance/README_FIRST.md`（当前状态唯一权威入口：版本、发布状态、分支概况）；
   - `docs/testing/黄金存档制度.md`（当前黄金存档与哈希）。
3. **发给 AI 的开场白（复制改改即可）**：
   > 继续「开局一键爽玩」项目。先读 `docs/maintenance/README_FIRST.md`（当前状态）、
   > `docs/maintenance/维护与重构标准流程.md` 和 `AGENTS.md`，报告当前状态与待办。
   > 本次要干的活：〈粘贴玩家反馈原文，或一句话说需求〉。

## 1. 三种活走哪条路（速查表）

| 活 | 流程 | 你必须拍板的门 | 备注 |
|---|---|---|---|
| 讨论、问答、只读检查 | 不走流程，直接办 | 无 | 例如「现在什么状态」「查查这段逻辑」 |
| 玩家报 bug 的核实修复 | 先只读核实根因；纯文案/纯文档/不改 MOD 语义的机械修正＝**B 轻流程**；涉事件/作用域/效果/触发条件等 MOD 语义（哪怕只改一行）＝**C 或 A** | B：只在提交时说「提交」；C/A：门一 + 门三 | 一次对话内能走完 |
| 增加功能 | 加功能/重构＝**C**；全新领域或大重构＝**A 立项全流程** | 门一 + 门二（改动大时）+ 门三 | 2–4 轮对话 |
| mod 制作/校验/监测机制增强 | **A 立项全流程**（例：实机监测机制那一轮） | 门一 + 门二 + 门三 | 多轮，慢慢来 |

**判定口诀**：讨论问答只读直接办；小修一句话对齐即可；新功能/大重构 → A；加功能/重构 → C；拿不准从高不从低。涉及 MOD 语义、事件/作用域、生成器、AI 守卫、编码与本地化契约、存档兼容、跨模块、实机结果、构建/发布的，一律走重流程。

## 2. 每种活的完整动作（你只需要做这些）

### 2.1 玩家报 bug

1. **原文直接贴给 AI**，不要自己转述加工（防信息失真）。
2. AI 会：对照源码/原版数据核实根因 → 报「修什么 / 为什么 / 不修什么」→ 你回「可以」或「改哪」。
3. AI 改完跑静态门禁（普通小修按需 K3 复检；高风险任务走重流程、强制独立复检）→ 报结果 → 你明确说「提交」；推送必须等你说「推送」二字。
4. 需要玩家验证的：让 AI「部署测试包、起草玩家测试说明」，你转发玩家；回执后让 AI 判读归档。

### 2.2 增加功能

1. 说清想要什么（一句话即可，边界、可行性让 AI 用调研补足）。
2. **门一**：AI 报「范围 + 为什么 + 不做什么」→ 你拍板。
3. **门二**（改动大时）：AI 在当前对话提交分步方案（范围/步骤/风险/回滚/验收）→ 你拍板「照批」。确有长期复用价值时才更新职责对应的现有文档，不为流程格式新建文档，也不往已冻结的开发状态快照里追加。
4. AI 小步实现、每步跑门禁、K3 复检 → 你确认「提交」。
5. 实机点验（你或玩家进游戏点一遍）→ 合格才走正式发版。

### 2.3 机制增强（制作/校验/监测机制本身）

1. 说痛点即可（例：「实机监测不健全，要成熟固定化的监测机制」）。
2. AI 走 A 六步：对齐需求 → 调研 → 再对齐 → 分步方案 → K3 审方案 → 小步实现 + diff 复检 + 提交。
3. 你只在三扇门拍板，其余 AI 自主推进。

## 3. 三扇门（全项目只这三处必须等你，其余 AI 自主）

| 门 | 时机 | 你的批复词 |
|---|---|---|
| 门一 需求对齐 | AI 报「做什么/不做什么」之后 | 「选 n」/「按推荐」/「可以」「不行」「范围改成…」 |
| 门二 方案拍板 | 方案落盘之后（A 必设；C 改动大才设） | 「选 n」/「按推荐」/「照批」「修改后再说」 |
| 门三 提交确认 | AI 报改动摘要 + 门禁结果之后 | 明确说「提交」；推送必须另说「推送」二字（两者均不得由「选 n」「按推荐」「确认」「照批」推断） |

门一/门二 AI 都会附 2–4 个建议选项（弹窗可点选；推荐项带「（推荐）」标注、每项一句取舍），你回「选 n」或「按推荐」即拍板；也可以自由说别的，不锁死。门三的「提交」和「推送」不设选项，必须你明确说出。

常用表达（自然语言示例，不是口令，怎么说都有效）：`选 n` / `按推荐` / `可以` / `照批` / `暂缓` / `关闭` / `列入待办`。**唯二的明确授权词**：`提交`、`推送`——必须你明确说出，AI 不得从其他话推断。

## 4. 每次改动后自动发生的事（你不用懂细节，只需知道会有这些）

- **静态门禁**：`validate_mod.py` / `test_validate_mod.py` / `generate_universal_mio_effect.py --check`（AI 跑，报 0 警告才算过）；
- **构建**（大改动/发版前）：`build_release.py` 出测试包 + SHA-256；
- **K3 独立复检**（重流程强制；普通小修按需）：本机 kimi 调 `moonshot/k3` 审方案/diff，修到「通过」，逐轮留痕；
- **实机回归**：部署到本地 MOD 目录 → 进游戏点验 → `check_logs.py` 判读 → 按 `docs/testing/实机回归归档制度.md` 归档；
- **黄金存档**：判定通过的存档按六项登记（见 `docs/testing/黄金存档制度.md`）；
- **收工登记**：当前状态有变化时同步 `docs/maintenance/README_FIRST.md` 对应现状行（带核实日期），需要时提交推送。

## 5. 你的授权词与常用表达速查（复制即用）

> 除「提交」「推送」外均为自然语言示例，不是必须说出的口令，普通表达同样有效；「提交」「推送」是明确授权词，必须你明确说出，不得从其他话推断。

| 场景 | 你说 |
|---|---|
| 开工 | 「继续项目，先读 README_FIRST 报告状态与待办」 |
| 修 bug | 「玩家报：〈原文〉。核实修复」 |
| 加功能 | 「想加：〈一句话〉。走 C/A 流程」 |
| 机制增强 | 「机制痛点：〈一句话〉。走 A 立项」 |
| 提交 / 推送 | 「提交」「推送」（严格分开，明确授权词） |
| 到门选建议 | 「选 1」「按推荐」（或点弹窗；仅限门一/门二） |
| 交玩家复测 | 「部署测试包，起草玩家测试说明」 |
| 收工 | 「此事列入待办，确保别的电脑拉取也能看到」 |
| 对齐 tool-library | 「给我一段话对齐 tool-library」 |
| 盘点玩家反馈 | 「对照用户反馈逐条核实：哪些完成、哪些没完成」 |

## 6. 常见疑问

- **我不懂技术怎么办？** 你只需会三件事：贴原文、到门用自然语言拍板、提交与推送时明确说出授权词。其余 AI 全包。
- **玩家反馈一大堆怎么处理？** 让 AI 先「逐条对照源码/文档核实现状，输出 完成/未完成/待拍板 清单」，再按清单分批立项。
- **换电脑了怎么接上？** `git pull` → 读 `docs/maintenance/README_FIRST.md` → 说「继续项目」。
- **黄金存档是什么？** 判定通过的可复现存档；下轮回归从它出发，保证前后可对比、谁跑偏谁现形。
- **实机回归怎么跑？** 说「按实机回归制度部署并给我操作步骤」，AI 会给出「进游戏点哪几步」的清单；游戏内还有自检套件（`effect PRC PRC_OCS_selftest_run_suite`）自动喊 50 项过不过。
