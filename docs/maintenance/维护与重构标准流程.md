# 维护与重构标准流程

> 固化时间：2026-08-18，与机主对齐确认。首案：本流程自身固化任务按本流程执行，留痕见附录 A。
> 定位：动手之前的强制流程。与 AGENTS.md「修改红线」「验证与发布门禁」衔接——本流程管动手前，红线管改动之中，验证与发布门禁管动手后；发布（构建/工坊/GitHub Release）仍按既有发布门禁，不在本流程内。
> 适用范围：一律强制——维护、重构、新功能、文档改动（含本流程文档本身）。

## 一、三级流程（先判级，三问定档，拿不准从高不从低）

1. 是已有功能还是新功能/跨模块大重构？新功能/大重构 → A。
2. 改动多大？局部几行改 bug/文案 → B；加功能/重构/依赖升级 → C。
3. 影响面？C 中动安全/数据格式/跨机，或预计超约 200 行或 5 个文件 → ④ 方案必须等机主拍板（门二）。

### A. 立项全流程（新功能、大规模重构；六步）

| 步 | 内容 | 门 |
|---|---|---|
| ① 对齐需求 | 与机主确认做什么/边界/不做什么；问答原文与结论记入方案文档「需求」节 | 门一：机主拍板才进② |
| ② 调研 | 查成熟开源实现与官方说明（引擎 effects 文档、官方 wiki、工坊同类 MOD），结论附出处；本机可实测的并行实测 | 自主推进 |
| ③ 再次对齐 | 带调研结论回机主核对方向；方向变更需机主认可 | 自主推进 |
| ④ 分步方案 | 方案文档落盘：需求、调研、分步改动点、风险、回滚、验收标准 | 门二：机主拍板才进⑤ |
| ⑤ 高级 AI 复检 | 审方案：把方案文档与验收标准交 K3 独立审计（执行口径见第三节），输出「通过/需修改+问题位置+修改思路」，修到通过 | 方案复检通过才进⑥ |
| ⑥ 经确认提交 | 小步实现（每步过 AGENTS.md 验证门禁，含构建）→ 改动 diff 经 K3 复检通过 → 机主确认 → git commit | 门三：机主确认才提交；推送仅凭「推送」二字 |

### B. 轻流程（小修/改 bug/文案）

对齐改什么（一句话说清）→ 改 → K3 复检（审 diff）→ 机主确认提交。在交接文档 `docs/maintenance/开发状态快照与交接.md` 追加「变更记录」小节，不另起炉灶。

### C. 维护升级流程（加功能、重构、依赖升级）

| 步 | 内容 | 门 |
|---|---|---|
| ① 对齐改什么 | 报改动范围+为什么+不改什么；记入变更记录草稿 | 门一：机主拍板 |
| ② 立基线 | git 提交干净基线；跑静态门禁留底（validate/unittest/mio --check，不含构建） | 自主推进 |
| ③ 轻调研 | 只在进新领域才调研（新引擎命令/新机制/新 DLC），否则跳过 | 自主推进 |
| ④ 分步方案 | 交接文档追加「变更记录 #n」：日期/需求/方案/验收/回滚 | 门二按阈值：动安全/数据格式/跨机或改动大才等机主拍板 |
| ⑤ 小步实现+每步回归 | 每步改完先跑静态门禁（validate/unittest/mio --check，旧功能不破）再验新功能 | 自主推进 |
| ⑥ K3 复检 | 审本次 diff，修到通过，逐轮记录 | 通过才进⑦ |
| ⑦ 经确认提交 | 机主确认 → git commit；同步更新受影响文档 | 门三；推送仅凭「推送」二字 |

## 二、三扇门（必须等机主拍板，其余自主推进）

1. 需求对齐（A①/C① 结束）；2. 方案拍板（A④ 必设，C④ 按阈值）；3. 提交确认（A⑥/C⑦/B 结束）。
另：推送仅凭「推送」二字；构建/发布/工坊上传按 AGENTS.md 发布门禁，不因本流程缩短。

## 三、K3 复检执行口径（2026-08-18 实测固化）

- 执行：本机 kimi CLI，命令 `kimi -m moonshot/k3 -p 审计提示词`；专用 API key 由机主提供、只存本机 kimi CLI 配置，永不入库、永不进文档。
- 给审计看：本次方案/改动 diff、验收标准与相关红线；要求输出「通过 / 需修改 + 问题位置 + 修改思路」，片段 ≤5 行，禁止泛泛而谈，不输出完整代码。
- 需修改的落实后必须再次复检，修到通过为止；每轮结论与修复落点记录在案。
- 通道背景（留档）：codex CLI 无法用该专用 key 调 K3——Moonshot /v1/responses 未开放（403）、codex 0.146 不支持 chat 线、DeepSeek 端点拒该 key（401）；kimi CLI + moonshot/k3 实测可用。日后通道变化以当时可用者为准，不跳步。

## 四、与既有门禁的衔接

本流程（动手前）→ AGENTS.md 修改红线（改动之中）+验证门禁（改动之后）→ 实机回归 → 文档 → 构建与 SHA → 维护者确认 → 标签/Release。内容改动后必须依次执行（发布类操作先 list_files tools/ 并读 docs/DEVELOPMENT.md 对应章节）：

    python tools/validate_mod.py
    python -m unittest tools.test_validate_mod
    python tools/generate_universal_mio_effect.py --check
    python tools/build_release.py

每步回归强度分级：A 流程每步过完整四步门禁（含构建）；C 流程每步只跑静态三条（validate/unittest/mio --check，不含构建），构建留到发布准备，与交接文档 §4.5（v2.8 变更记录 #2）实执记录一致。

实机回归环节（2026-08-19 起，与「实机监测机制」A 立项衔接）：实测后按 `docs/testing/实机回归归档制度.md` 归档入库，判读用 `tools/check_logs.py`、编排用 `tools/run_regression.ps1`（工具存在才生效；未落地前沿用既有实机口径）。

## 五、纪律

1. 一律强制：维护、重构、功能、文档改动均走本流程；未经确认不动手、不提交。
2. 全程留痕：对齐问答、调研出处、方案、验证记录、K3 逐轮历程全部落盘。
3. 密钥红线：专用 key 等机密永不入库、永不进文档。
4. 基线先行（C 流程）：动手前先 git 提交干净基线；每步回归旧功能——维护最大的风险是修坏旧功能。
5. 提交信息中文摘要式短句；提交与推送分离，推送仅凭「推送」二字。
