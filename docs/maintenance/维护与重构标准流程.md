# 维护与重构标准流程

> 固化时间：2026-08-18，与机主对齐确认。首案：本流程自身固化任务按本流程执行，留痕见附录 A。
> 定位：动手之前的强制流程。与 AGENTS.md「自然语言任务路由」「修改红线」衔接——路由管判级入口，本流程管动手前，红线管改动之中，验证与发布细节（`docs/DEVELOPMENT.md`）管动手后；发布（构建/工坊/GitHub Release）仍按 `docs/DEVELOPMENT.md` 发布门禁，不在本流程内。
> 适用范围：实际改动（维护、重构、新功能、文档改动，含本流程文档本身）按本流程判级；普通讨论、问答与只读检查不走流程（见第〇节）。

## 〇、中度简化（2026-09-05 机主拍板）

- **普通讨论、问答和只读检查**：直接处理，不启动本流程。
- **普通小修**（小型、可逆、范围明确的文案、纯文档和机械性小修）：一句话对齐后即可实施；K3 等独立复检为按需（机主不满意、有疑点时可随时要求）；不强制向 `开发状态快照与交接.md` 追加变更记录（该文档已冻结为历史档案）；引起当前状态变化的小修，只更新 `docs/maintenance/README_FIRST.md` 对应现状行并带核实日期；完成后仍须机主明确说出「提交」才可 git commit。
- **升级条件**：任务一旦命中以下任一条件，必须退出 B、升级为 A/C 重流程，并保留方案拍板、强制独立复检与对应验证——MOD 语义、事件或作用域、生成器、AI 守卫、编码与本地化契约、存档兼容、跨模块、实机结果、构建或发布。不得出现「高风险仍留在 B、只是按需复检」的口径。
- **明确授权词**：日常任务可用自然语言启动与执行；「提交」与「推送」分别需机主明确说出（自然语言表达即可），不得从「确认」「照批」「按推荐」等拍板词推断。

## 一、三级流程（先判级，三问定档，拿不准从高不从低）

1. 是已有功能还是新功能/跨模块大重构？新功能/大重构 → A。
2. 改动性质？纯文案、纯文档或不改变 MOD 语义的机械修正 → B；加功能/重构/依赖升级 → C。**不按「只有几行」判 B**：玩家反馈先只读核实根因再判级；涉及事件、作用域、效果、触发条件等 MOD 语义，即使只改一行也升级 A/C。
3. 影响面？C 中动安全/数据格式/跨机，或预计超约 200 行或 5 个文件 → ④ 方案必须等机主拍板（门二）。

### A. 立项全流程（新功能、大规模重构；六步）

| 步 | 内容 | 门 |
|---|---|---|
| ① 对齐需求 | 与机主确认做什么/边界/不做什么；问答原文与结论记入方案文档「需求」节 | 门一：机主拍板才进②（报告带选项） |
| ② 调研 | 查成熟开源实现与官方说明（引擎 effects 文档、官方 wiki、工坊同类 MOD），结论附出处；本机可实测的并行实测 | 自主推进 |
| ③ 再次对齐 | 带调研结论回机主核对方向；方向变更需机主认可 | 自主推进 |
| ④ 分步方案 | 方案文档落盘：需求、调研、分步改动点、风险、回滚、验收标准 | 门二：机主拍板才进⑤（报告带选项） |
| ⑤ 高级 AI 复检 | 审方案：把方案文档与验收标准交 K3 独立审计（执行口径见第三节），输出「通过/需修改+问题位置+修改思路」，修到通过 | 方案复检通过才进⑥ |
| ⑥ 经确认提交 | 小步实现（每步过 `docs/DEVELOPMENT.md` 验证门禁，含构建）→ 改动 diff 经 K3 复检通过 → 机主明确说「提交」→ git commit | 门三：机主明确授权才提交；推送仅凭「推送」二字 |

### B. 轻流程（普通小修：纯文案/纯文档/不改 MOD 语义的机械修正）

对齐改什么（一句话说清；玩家反馈先只读核实根因再判级）→ 改 → 机主明确说「提交」才提交。K3 独立复检为按需（机主不满意或有疑点时）；命中第〇节升级条件的任务不得留在 B，必须升级为 A/C 并恢复强制独立复检。不再向 `docs/maintenance/开发状态快照与交接.md` 追加变更记录（已冻结为历史档案）；引起当前状态变化的小修，只更新 `docs/maintenance/README_FIRST.md` 的对应现状行并带核实日期。

### C. 维护升级流程（加功能、重构、依赖升级）

| 步 | 内容 | 门 |
|---|---|---|
| ① 对齐改什么 | 报改动范围+为什么+不改什么，在当前任务中说明范围、验收与回滚 | 门一：机主拍板（报告带选项） |
| ② 立基线 | 记录当前 HEAD 与 git status，确认任务涉及路径没有未处理改动（不得为制造干净基线而自动提交机主改动；既有改动与任务重叠即停止并报告）；跑静态门禁留底（validate/unittest/mio --check，不含构建） | 自主推进 |
| ③ 轻调研 | 只在进新领域才调研（新引擎命令/新机制/新 DLC），否则跳过 | 自主推进 |
| ④ 分步方案 | 在当前任务中提交分步方案（需求/分步改动点/风险/回滚/验收）；确有长期复用价值时才更新职责对应的现有文档，不为流程格式新建文档，不得向已冻结的开发状态快照追加内容 | 门二按阈值：动安全/数据格式/跨机或改动大才等机主拍板（报告带选项） |
| ⑤ 小步实现+每步回归 | 每步改完先跑静态门禁（validate/unittest/mio --check，旧功能不破）再验新功能 | 自主推进 |
| ⑥ K3 复检 | 审本次 diff，修到通过，逐轮记录 | 通过才进⑦ |
| ⑦ 经确认提交 | 机主明确说「提交」→ git commit；同步更新受影响文档 | 门三：机主明确授权才提交；推送仅凭「推送」二字 |

## 二、三扇门（必须等机主拍板，其余自主推进）

1. 需求对齐（A①/C① 结束）；2. 方案拍板（A④ 必设，C④ 按阈值）；3. 提交确认（A⑥/C⑦/B 结束）。
另：「提交」与「推送」均不进选项——分别需机主明确说出的授权词，不得从「确认」「照批」「按推荐」推断；推送仍仅凭「推送」二字。构建/发布/工坊上传按 `docs/DEVELOPMENT.md` 发布门禁，不因本流程缩短。

### 带选项报告（2026-08-20 起）

门一（需求对齐）/门二（方案拍板）到门时，AI 门报告＝正文＋建议选项：
- 给出 2–4 个建议选项，推荐项第一位并标「（推荐）」，每项附一句取舍/影响说明；
- 呈现：正文照发＋选项以弹窗可点选（本环境 `ask_user_question`）；无弹窗工具或弹窗不可用的环境，降级为正文编号列表；
- 回复：机主点选、回「选 n」「按推荐」即视为该门拍板并生效；选项之外自由说别的照旧，不锁死；
- 边界：选项拍板只适用于门一/门二。门三（提交确认）不提供选项：AI 只报告改动与验证结果，随后等待机主明确说出「提交」；「提交」与「推送」分别需机主明确说出的授权词（自然语言表达即可，但不得由「确认」「照批」「按推荐」推断）。

## 三、K3 复检执行口径（2026-08-18 实测固化）

- 执行：本机 kimi CLI，命令 `kimi -m moonshot/k3 -p 审计提示词`；专用 API key 由机主提供、只存本机 kimi CLI 配置，永不入库、永不进文档。
- 给审计看：本次方案/改动 diff、验收标准与相关红线；要求输出「通过 / 需修改 + 问题位置 + 修改思路」，片段 ≤5 行，禁止泛泛而谈，不输出完整代码。
- 需修改的落实后必须再次复检，修到通过为止；每轮结论与修复落点记录在案。
- 通道背景（留档）：codex CLI 无法用该专用 key 调 K3——Moonshot /v1/responses 未开放（403）、codex 0.146 不支持 chat 线、DeepSeek 端点拒该 key（401）；kimi CLI + moonshot/k3 实测可用。日后通道变化以当时可用者为准，不跳步。

## 四、与既有门禁的衔接

本流程（动手前）→ AGENTS.md 修改红线（改动之中）→ 验证门禁（改动之后）→ 实机回归 → 文档 → 构建与 SHA → 维护者确认 → 标签/Release。验证命令、构建与发布操作细节以 `docs/DEVELOPMENT.md` 为唯一权威（本地检查/CWTools/实机回归/构建/工坊上传各节）；发布类操作先列出 `tools/` 并读对应章节。

改动后验证范围按内容定级：需要构建与实机回归的是 MOD 源码、生成产物或发布内容变更；纯文档小修只运行与其风险相称的检查（如 `git diff --check`、指针/链接检查、针对性静态检查），不为形式构建发布包。

每步回归强度分级：A 流程每步过完整门禁（静态＋构建）；C 流程每步只跑静态三条（validate/unittest/mio --check，不含构建），构建留到发布准备，与交接文档 §4.5（v2.8 变更记录 #2）实执记录一致。

实机回归环节（2026-08-19 起，与「实机监测机制」A 立项衔接）：实测后按 `docs/testing/实机回归归档制度.md` 归档入库，判读用 `tools/check_logs.py`、编排用 `tools/run_regression.ps1`（工具存在才生效；未落地前沿用既有实机口径）。

## 五、纪律

1. 一律强制：维护、重构、功能、文档改动均走本流程；未经确认不动手、不提交。
2. 可复核留痕（限 A/C 重流程）：范围、方案、关键依据、验证结果与 K3 结论须在当前任务交付中可复核；只有对后续维护有长期价值的结论才更新职责对应的现有文档，不要求把问答和逐轮过程全部落盘；B 普通小修不强制专门落盘、不强制 K3。
3. 密钥红线：专用 key 等机密永不入库、永不进文档。
4. 基线先行（C 流程）：动手前先记录 HEAD 与 git status、确认任务涉及路径无未处理改动；不得为制造干净基线而自动提交机主改动，既有改动与任务重叠即停止并报告。每步回归旧功能——维护最大的风险是修坏旧功能。
5. 提交信息中文摘要式短句；提交与推送分离，推送仅凭「推送」二字。
6. 门报告带选项（2026-08-20 起）：门一/门二到门时，AI 报告同步给 2–4 个建议选项（推荐第一标「（推荐）」、每项一句取舍），机主点选或回「选 n」/「按推荐」即拍板生效、自由回复不锁死；弹窗不可用降级正文编号列表；门三只报告改动与验证结果，「提交」「推送」永不进选项。
