> 立项时间：2026-08-19。流程依据：`docs/maintenance/维护与重构标准流程.md` A 全流程（新机制建设，走 A 六步）。
> 状态：①对齐需求（门一**待机主拍板**）→ ②调研（已完成：外部调研＋本仓盘点＋本机官方文档实测三路，见第三、二节）→ ③再次对齐（本文四节候选方向，待机主定方向）→ ④分步方案（门二，待本批拍板后编写）→ ⑤K3 复检 → ⑥经确认提交（门三；推送仅凭「推送」二字）。
> 定位：把「需要进游戏实测」的验证环节，从纯人工点验升级为成熟、固定化、可留痕的监测机制。本批只立项与调研，不动 MOD 功能代码。

## 一、需求（门一：待机主拍板）

### 1.1 机主原话

> 「一键开局立项，现在，我们的监测的机制还不健全，特别是那种需要进游戏实测的，我认为应该有成熟的，固定化的监测机制，需要进行一波调研并吸纳进来。」

### 1.2 AI 对齐理解

- **问题**：现有监测机制不健全，最薄弱的是「进游戏实测」环节——该环节目前纯人工、无固定流程、证据多次断档、错误靠运气撞见（佐证见第二节）。
- **要做**：调研业界/社区成熟做法，形成**标准化、固定化**的实测监测机制，并**吸纳**进本项目（工具/流程/留痕入仓，与本仓既有门禁衔接）。
- **关键词**：监测机制＝发现问题的机制，重点覆盖静态门禁抓不到、必须实机才能暴露的缺陷；固定化＝步骤、工具、模板、留痕可重复可核对；成熟＝有业界或社区先例支撑，不另造轮子。
- **产出物预期**：调研报告＋分步方案＋落地工具/模板/文档（本批先出前三者，落地待门二拍板后小步实施）。

### 1.3 边界（待机主确认）

1. 不改变 MOD 面向玩家的运行时行为：自检能力走 debug/console 通道，不影响正常游玩与「AI 守卫」等既有红线。
2. 不追求「全自动无人测试」：游戏 GUI 无法无头启动，实机仍需人点；本批目标是**把人点之外的环节全部固定化、自动化、留痕化**。
3. 本批不改任何游戏功能代码；新增工具/脚本按仓库门禁（validate/unittest/mio --check/build）验收。
4. 证据脱敏：日志含本机路径/用户名，入库前按 `docs/DEVELOPMENT.md` 既有口径脱敏。
5. 不复制已有能力：现有静态门禁、CI（`.github/workflows/validate.yml`）、部署脚本继续沿用，新机制只补「实机」空缺并与其衔接。

### 1.4 门一待拍板问题

1. **范围**：本批只做「进游戏实测监测」，还是把静态门禁＋实机监测＋证据归档合成一套统一监测体系？
2. **形态**：接受在 MOD 内新增 debug 门控的自检事件/效果（随发布包分发，但玩家不可见、AI 不可用）吗？还是监测能力必须全部放在 MOD 之外（工具/存档/日志解析）？
3. **自动化边界**：接受「维护者手动点验 + AI 自动判读、归档、出报告」的半自动分工吗（这是 `docs/DEVELOPMENT.md` 已授权分工的自然延伸）？
4. **证据强度**：是否要求每轮实机回归都做到「仓库内可独立复核」（日志/截图/自检输出入仓），废除「只记维护者结论」的做法？

## 二、现状痛点（本仓盘点，2026-08-19 盘点子代理逐文件核实）

## 三、调研（A ②）

### 3.1 外部成熟机制调研（来源与证据强度见各条）

> 可靠性标注：★★★★ 官方文档/引擎实文件；★★★ 广泛使用工具/官方百科；★★ 社区实践/个人先例；★ 未查证传闻。外部调研子代理报告到达后如有新增来源将补正。

#### 3.1.1 Paradox 官方与引擎自带

- **引擎自带场景断言测试框架**（★★★★）：游戏根目录 `tests\*.txt` 的 `success`/`fail` 触发器断言格式与 `scenario_testing.log` 通道，即 Paradox 自家「进游戏实测」的固定化机制（本机实文件已核，见 3.2 节第 12 条）。
- **console 测试原语**（★★★★）：`run`/`effect`/`event`/`testevent`/`savecheck`/`test_log`/`test_save_mode`/`debug` 均在游戏自带 `documentation\console_commands_documentation.md` 有正式条目（见 3.2 节）。社区维基同收：Hearts of Iron 4 Wiki [Console commands](https://hoi4.paradoxwikis.com/index.php?title=Console_commands&oldid=62089)（★★★）。
  - ⚠️ 证据冲突与裁定：社区 wiki 称「HOI4 没有 EU4 那种 `run <文件>`」（[wiki Effect 页](https://hoi4.paradoxwikis.com/index.php?title=Effect&diff=98402&oldid=24355)与 EU4 文档 [vawser/EU4-Documentation](https://github.com/vawser/EU4-Documentation/blob/master/effects.txt) 口径），但**本机游戏自带官方文档（1.19.2）明确收录 `run`＝「Runs the specified file with list of commands」**。裁定：以本机游戏文档为最高证据（wiki 落后于版本），`run` 存在；其脚本文件存放路径官方未载明，列为「本机实测待确认」（见 4.7）。
- **游戏内断言官方原语**（★★★★）：effects `log` 写 game.log（本机文档行 4802）；wiki 记载 **`debug = yes` 可加在 meta effect（scripted effect/trigger 头部），把该块求值结果追加进 game.log**（[wiki Effect](https://hoi4.paradoxwikis.com/index.php?title=Effect&diff=98402&oldid=69340)、[wiki Triggers](https://hoi4.paradoxwikis.com/index.php?title=Triggers&diff=cur&oldid=59483)）——比 `log` 更省力的留痕手段；`list_flags`（运行时列出激活 flag）、`reload [<type>]`（按类型热重载，免重启迭代）同为官方查询/迭代原语（[wiki Console commands](https://hoi4.paradoxwikis.com/Console_commands)）。
- **官方调试入口**（★★★★）：启动器内置「以调试模式打开游戏」＝`-debug_mode`（本机 `launcher-settings.json` 实文件）；wiki Modding 页佐证 debug 模式解锁开发者专属命令、有错误时 error.log 载入自动弹出（[wiki Modding](https://hoi4.paradoxwikis.com/index.php?diff=67142&oldid=65685&title=Modding)）。完整启动参数表 wiki 页被反爬拦截、未取得权威清单（未查证项）。
- **隐藏 debug 事件/决议自检范式**（★★★）：事件/决议 `hidden = yes` 不打扰玩家、`fire_only_once = yes` 单次执行，控制台 `event`/`eval_effect` 触发——社区通用做法（[wiki Event_modding](https://hoi4.paradoxwikis.com/index.php?title=Event_modding)、[wiki Decision_modding](https://hoi4.paradoxwikis.com/index.php?title=Decision_modding&diff=72902&oldid=65229)）。
- **开发者命令解锁生态**（★★）：社区存在 [rxzyx/paradox-developer-commands](https://github.com/rxzyx/paradox-developer-commands)（解锁 HOI4/EU4 developer commands），佐证 debug 模式生态成熟。

#### 3.1.2 社区工具链

- **The Validator / 社区工具清单**（★★）：[HOI4 Modding Fandom · Tools](https://hoi4-modding.fandom.com/wiki/Tools) 收录的老牌 MOD 校验/调试工具清单（含 Validator 等）；本项目静态门禁已覆盖其大部分静态能力，其实机能力为零。
- **Irony Mod Manager**（★★★）：[bcssov/IronyModManager](https://github.com/bcssov/IronyModManager)（含[官方 FAQ](https://bcssov.github.io/IronyModManager/faq.html)）——MOD 冲突检测/合并查看器，广泛使用；对本项目价值＝排查第三方 MOD 干扰（如 daliwan 类杂音）的既成工具，而非自建。
- **Pdx-Unlimiter**（★★★）：[crschnick/pdx_unlimiter](https://github.com/crschnick/pdx_unlimiter)（另有 Steam 物品 4170030）——全系 Paradox 存档管理器/编辑器，成熟维护；可作存档核对的现成 GUI/半自动工具，其解析库能否被本仓 Python 直接复用需门二评估。
- **cwtools + GitHub Action**（★★★）：[CWTools Action](https://github.com/marketplace/actions/cwtools-action)——Paradox 脚本解析/校验的现成 CI 组件；对 HOI4 的支持程度以官方说明为准，属「静态校验进 CI」的成熟先例（本项目 CI 已自研等效门禁，仅作对照）。

#### 3.1.3 游戏 QA 通用成熟机制（★★ 通用工程实践，非单一出处）

- **冒烟/回归套件固定化**：固定测试档（golden save/黄金存档）＋固定操作序列（脚本化 console 指令）＋逐项断言清单，是本行业处理「必须实机跑」的标准组合；本项目 test1–test5.hoi4 已是雏形，缺固定化制度。
- **日志基线白名单**：已知噪音白名单化＋「新出现错误类型」告警（baseline diff），对应本仓散落 markdown 的人工白名单（2.4 节）。
- **结构化结果留痕**：回归结果机器可读（JSON），支持跨轮 diff 与趋势比对，对应本仓「清单 markdown 人工填、多次留空」的断档（2.2 节）。
- **人工判定与自动判定分层**：GUI 画面/手感仍由人判（测试预言 test oracle），可脚本化断言交给引擎/工具判——本立项即按此分层设计（4.1–4.6）。

#### 3.1.4 CI＋游戏日志解析先例

- Paradox MOD 社区常见做法＝静态校验进 CI（cwtools、自研 validate）；**把实机游戏日志喂 CI 的公开先例极少**（游戏不可无头、日志含本机隐私），检索未发现权威先例（★未查证充分，落地仍以本机半自动为主、CI 仅可选做日志产物归档校验）。

#### 3.1.5 外部调研小结

业界成熟做法与本立项候选方向一一对应：引擎断言测试（官方 tests 框架）→ 4.1；固定脚本＋黄金存档（QA 通用）→ 4.2；日志基线白名单（QA 通用）→ 4.3；存档核对（Pdx-Unlimiter 先例）→ 4.4；结构化留痕（QA 通用）→ 4.5；编排门禁（本仓流程需求）→ 4.6。无一处需要自造轮子，均有先例可依。

## 四、可吸纳方向（候选，供再次对齐与门二）

> 按「游戏内自检 / 控制台脚本驱动 / 日志基线判读 / 存档断言 / 证据留痕归档 / 流程固化」六类归纳；外部调研结论到达后校正补充。

### 4.1 游戏内自检（MOD 内 debug 门控断言套件）

- 依据：effects `log`（可写 game.log，可本地化）＋触发器/效果断言能力（`if/else` + `log` 输出 PASS/FAIL 标记）＋官方 `tests\*.txt` 场景断言格式（success/fail 触发器）为范式。
- 形态候选：新增 debug 门控事件/效果（如 `PRC_OCS.9xxx` 自检事件链），对关键功能做游戏内断言：flag 已设、科技已授、装备已入库存、MIO 资金/规模、决议可用性；每条断言输出 `[OCS_TEST] PASS/FAIL <case>` 到 game.log。
- 门控红线：玩家不可见、AI 不可用（`is_ai = no` 守卫照旧）、不进正式玩家路径；是否随发布包分发待门一拍板。
- 优点：把「人眼看界面」变为「引擎自己判」，覆盖 effect 有效性/DLC 极性/语义错位等静态抓不到的错误类型；缺点：需新增游戏脚本，验收依赖实机触发一次。

### 4.2 控制台脚本驱动（固定实测脚本 + 黄金存档）

- 依据：console `run`（执行命令文件）、`effect <tag> <scripted_effect>`、`event <id> <tag>`、`testevent`（事件合法性冒烟）、`savecheck`（存档往返一致性）、`debug`/`-debug_mode` 官方入口；`console_history.txt` 可审计操作。
- 形态候选：每轮实测用固定 `run` 脚本（切国家→触发自检事件→执行点验效果→自动存判定档），配套「黄金存档」（test1–test5 升格为制度：版本化、留档、随轮复用），人只负责启动游戏与执行一条命令。
- 优点：操作序列可重复、可审计、可复现；缺点：`run` 脚本文件位置需本机实测确认（候选：游戏根目录相对路径）。

### 4.3 日志基线判读（机器白名单 + 自动判读工具）

- 依据：现有四份日志＋23 个日志资产；噪音白名单现散落 markdown；本机 `error.log` 活证据。
- 形态候选：`tools/check_logs.py` 之类——机器可读白名单文件（已知噪音模式：gamelobby/remotefile、Conflict Risk、daliwan Invalid supported_version 等）＋「本轮 vs 基线」diff 告警＋`[OCS_TEST]` 标记提取＋`code_revisions.log` 版本绑定＋结果 JSON 落盘。
- 优点：把「人脑经验」固化进仓库、可 CI 复用（若上传日志）或本机复用；缺点：白名单需随原版更新维护。

### 4.4 存档断言（.hoi4 解析）

- 依据：二进制存档 48–68 MB 已在本机；当前无解析先例（调研中确认成熟解析库/格式说明）。
- 形态候选：解析存档核对 MIO 特质/资金、科技、装备库存、模板等「界面上看不见全貌」的状态；或退而用「引擎自检事件 + log」间接断言（4.1 已覆盖大部分，存档解析仅补深度核对）。
- 优点：独立于游戏内埋点、可事后核对；缺点：格式未公开、实现成本最高，是否值得做待门二评估（4.1 或可覆盖其九成需求）。

### 4.5 证据留痕归档（强制入库 + 结构化产物）

- 依据：v2.6-test2/v2.7-test1/v2.8-test1 清单空白、截图缺失、日志未入库的多轮断档；`docs/DEVELOPMENT.md` 已要求「仓库内可独立复核证据」与脱敏。
- 形态候选：`docs/testing/<版本-轮次>/` 归档目录约定（清单 JSON 化、日志脱敏副本、截图命名规范、SHA-256 清单）；回归清单模板改为「逐项必填 + 缺证据＝不通过」；AI 判读工具产出机器可读结果供 diff/趋势比对。
- 优点：直接堵住历史上最大的断档点；缺点：无技术风险，纯纪律+工具，成本低。

### 4.6 流程固化（实机回归门禁脚本 + 编排）

- 依据：现状部署→启动→采集→判读全链路无编排；A/C 流程要求每步回归留痕。
- 形态候选：`tools/run_regression.ps1` 之类编排——部署测试包→清旧日志→提示维护者启动实测→回收日志/存档/截图→跑判读工具→生成回归报告→归档；把 `docs/maintenance/维护与重构标准流程.md` 的「实机回归」环节接到固定脚本上。
- 优点：一命令串起全链路；缺点：启动游戏这一步仍需人手（无头自动化不可行），编排脚本只做前后置。

### 4.7 校正与开放项（外部调研合并后）

- 已校正：4.4 存档断言的成熟先例＝Pdx-Unlimiter（★★★），其解析库复用性待门二评估；4.2 的 `run` 脚本文件位置仍待本机实测确认（官方文档未载明路径，EU4 先例提示可放 mod 文件夹）。
