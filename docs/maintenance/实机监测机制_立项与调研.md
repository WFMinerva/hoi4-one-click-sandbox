# 实机监测机制 · 立项与调研（A 流程 ①–③）

> 立项时间：2026-08-19。流程依据：`docs/maintenance/维护与重构标准流程.md` A 全流程（新机制建设，走 A 六步）。
> 状态：①对齐需求（门一**待机主拍板**）→ ②调研（已完成，见第三节）→ ③再次对齐（本文，待机主定方向）→ ④分步方案（门二，待本批拍板后编写）→ ⑤K3 复检 → ⑥经确认提交（门三；推送仅凭「推送」二字）。
> 定位：把「需要进游戏实测」的验证环节，从纯人工点验升级为成熟、固定化、可留痕的监测机制。本批只立项与调研，不动 MOD 功能代码。

## 一、需求（门一：待机主拍板）

### 1.1 机主原话

> 「一键开局立项，现在，我们的监测的机制还不健全，特别是那种需要进游戏实测的，我认为应该有成熟的，固定化的监测机制，需要进行一波调研并吸纳进来。」

### 1.2 AI 对齐理解

- **问题**：现有监测机制不健全，最薄弱的是「进游戏实测」环节——该环节目前纯人工、无固定流程、证据多次断档、错误靠运气撞见（佐证见第二节）。
- **要做**：调研业界/社区成熟做法，形成**标准化、固定化**的实测监测机制，并**吸纳**进本项目（工具/流程/留痕入仓，与本仓既有门禁衔接）。
- **关键词**：监测机制＝发现问题的机制，重点覆盖静态门禁抓不到、必须实机才能暴露的缺陷；固定化＝步骤、工具、模板、留痕可重复可核对；成熟＝有业界或社区先例支撑，不另造轮子。
- **产出物预期**：调研报告＋分步方案＋落地工具/模板/文档（本批先出前三者，落地待门二拍板后小步实施）。

### 1.3 边界（待机主确认）

1. 不改变 MOD 面向玩家的运行时行为：自检能力走 debug/console 通道，不影响正常游玩与「AI 守卫」等既有红线。
2. 不追求「全自动无人测试」：游戏 GUI 无法无头启动，实机仍需人点；本批目标是**把人点之外的环节全部固定化、自动化、留痕化**。
3. 本批不改任何游戏功能代码；新增工具/脚本按仓库门禁（validate/unittest/mio --check/build）验收。
4. 证据脱敏：日志含本机路径/用户名，入库前按 `docs/DEVELOPMENT.md` 既有口径脱敏。
5. 不复制已有能力：现有静态门禁、CI（`.github/workflows/validate.yml`）、部署脚本继续沿用，新机制只补「实机」空缺并与其衔接。

### 1.4 门一待拍板问题

1. **范围**：本批只做「进游戏实测监测」，还是把静态门禁＋实机监测＋证据归档合成一套统一监测体系？
2. **形态**：接受在 MOD 内新增 debug 门控的自检事件/效果（随发布包分发，但玩家不可见、AI 不可用）吗？还是监测能力必须全部放在 MOD 之外（工具/存档/日志解析）？
3. **自动化边界**：接受「维护者手动点验 + AI 自动判读、归档、出报告」的半自动分工吗（这是 `docs/DEVELOPMENT.md` 已授权分工的自然延伸）？
4. **证据强度**：是否要求每轮实机回归都做到「仓库内可独立复核」（日志/截图/自检输出入仓），废除「只记维护者结论」的做法？

## 二、现状痛点（本仓盘点，2026-08-19 盘点子代理逐文件核实）

### 2.1 现有监测/验证机制一览

| 机制 | 类型 | 自动化 | 覆盖 | 不覆盖 |
|---|---|---|---|---|
| `tools/validate_mod.py` | 静态检查 | 全自动 | 文件存在性、descriptor↔packaging 一致、编码/BOM、本地化键对等、effect 重名、多 limit、AI 守卫、PRC 双 tag、受控州等红线 | effect 是否真实存在于引擎/作用域；DLC 分支极性；数值是否生效；文本渲染 |
| `tools/test_validate_mod.py` | 检查器自测＋31 条契约 | 全自动 | 解析器行为＋模板编制/MIO 计数/事件映射/菜单接线/骷髅师/B 系列修复契约 | 实机行为 |
| `generate_universal_mio_effect.py --check` | 生成产物一致性 | 全自动 | 共享 MIO 产物与生成器重建一致 | 游戏内 MIO 实际效果 |
| `tools/build_release.py` | 构建检查 | 全自动 | 确定性 ZIP、LF 统一、MANIFEST 复核、跨机字节级复现 | 游戏运行 |
| CI `.github/workflows/validate.yml` | 构建检查 | 全自动 | 三项检查＋构建＋两次构建哈希一致 | 无游戏环境，不可能实机 |
| `tools/deploy_to_local_mod.ps1` | 部署脚本 | 半自动 | robocopy 镜像、descriptor 核验、dlc_load 启用、VERIFY 报告 | 进游戏点验本身 |
| 维护者人工实机回归 | 人工实测 | 纯人工 | 逐项清单点验、四份日志、截图 | 留痕强制、可独立复核证据 |
| AI 日志判读 | 日志判读 | 半自动 | 白名单经验人脑执行 | 白名单未机器化 |
| K3 复检 / 用户反馈整理 | 半自动 | 半自动 | 方案与 diff 审计、反馈分档 | 不实跑门禁；依赖用户主动上报 |

一句话现状：**静态四门禁强、实机环节弱、留痕靠自觉**。

### 2.3 静态门禁抓不到的错误类型（均有实例）

1. effect 有效性/作用域：`enable_equipment_modules` 仅存在于科技/特殊科研专用作用域，被误移植进事件——静态 parser 无法验证 effect 是否真实存在（HJ 186）。
2. DLC 分支极性：B3 的 OR 极性反了，K3 复检前两轮才查出（HJ 120）。
3. 标签与效果语义错位：B4 通用模板套错 42 组选项标签（HJ 195）。
4. 隐藏块遮蔽：B5 `tech_effect|` 嵌进 `hidden_effect` 后不可见（HJ 196）。
5. 遗漏奖励项：B1 漏 `upgrade_training_centers`、B6 漏石墨/重水组、Issue 5 generic 迭代奖励缺口——**全部靠用户反馈暴露**（HJ 4.4/4.8 节）。

### 2.6 缺口清单（固定化实机监测要补的）

- **工具类**：日志自动回收/判读脚本；机器可读噪音白名单；`.hoi4` 存档解析器（自动核对 MIO 特质/模板/数值）；console 驱动/回放利用；effect 有效性引擎级校验。
- **流程类**：实机回归固定触发/门禁脚本；日志时间戳判定与脱敏固化；「最新一轮日志」定位标准。
- **留痕类**：截图/原始日志/逐项结果入库强制化；「维护者结论」与「仓库可复核证据」自动区分校验；测试轮次归档目录约定与结构化产物。
- **自动化类**：进游戏点验与截图比对无法自动化（无操作回放/画面校验）；部署→启动→采集→判读全链路无编排脚本；回归结果无 JSON 结构化产物，无法 diff/趋势比对。
